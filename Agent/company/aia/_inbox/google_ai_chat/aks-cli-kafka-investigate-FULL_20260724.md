## Q2
**You:** 1. การใช้ kubectl กับ az aks ต่างกันยังไง 2. ถ้าต้องการ ดู log ที่ เป็นการ start , restart kafka cluster ตรงนี้ดูได้ยังไง จาก command ไหนหรอครับ

**AI:** นี่คือคำอธิบายความแตกต่างและการตรวจสอบ Log ของ Kafka Cluster ครับ   1. ความแตกต่างระหว่าง az aks กับ kubectl มองง่ายๆ คือ az aks จัดการ "บ้าน" (Infrastructure) ส่วน kubectl จัดการ "คนในบ้าน" (Applications) ครับ   az aks (Azure CLI): หน้าที่: จัดการ Cloud Infrastructure ของ Microsoft Azure ตัวอย่างการใช้: สร้าง/ลบ คลัสเตอร์, เพิ่ม/ลดจำนวนเครื่องเซิร์ฟเวอร์ (Scale Nodes), อัปเกรดเวอร์ชัน Kubernetes (K8s Version) ขอบเขต: ทำงานจากภายนอกคลัสเตอร์ สั่งการไปยังระบบหลังบ้านของ Azure   kubectl (Kubernetes CLI): หน้าที่: จัดการ Application และสิ่งต่างๆ ที่รันอยู่ภายใน Kubernetes ตัวอย่างการใช้: สั่งรันแอปพลิเคชัน (Deploy Pods), ดู Log ของแอป, ตรวจสอบสถานะ Service, เข้าไปแก้ Config ข้างใน ขอบเขต: ทำงานอยู่ภายในคลัสเตอร์ (ต้องรัน az aks get-credentials ก่อนเพื่อขอสิทธิ์เข้าบ้าน)   2. วิธีดู Log การ Start / Restart ของ Kafka Cluster การดู Log ใน Kubernetes จะใช้คำสั่ง kubectl เป็นหลัก โดยต้องเช็กก่อนว่า Kafka ของคุณติดตั้งผ่านวิธีไหน (ส่วนใหญ่จะใช้ Strimzi Operator หรือ Helm Chart )   ทำตามขั้นตอน (Commands) เรียงตามนี้ได้เลยครับ:   ขั้นตอนที่ 1: หาชื่อ Pod ของ Kafka และ Namespace   ต้องรู้ก่อนว่า Kafka รันอยู่ใน Namespace ไหน และ Pod ชื่ออะไร   bash # แสดง Pod ทั้งหมดในทุก Namespace เพื่อหา Kafka
kubectl get pods --all-namespaces | grep kafka
Use code with caution. (สมมติว่าเจอใน Namespace ชื่อ kafka-prod และชื่อ Pod คือ kafka-cluster-kafka-0 )   ขั้นตอนที่ 2: ใช้คำสั่งดู Log   เลือกใช้คำสั่งตามสถานการณ์ที่คุณต้องการตรวจเช็กครับ:   ดู Log สดๆ แบบ Real-time (ตอนมันกำลัง Start): bash kubectl logs -f kafka-cluster-kafka- 0 -n kafka-prod
Use code with caution. ดู Log ย้อนหลัง (กรณีถ้าระบบเพิ่ง Restart ไปแล้วอยากรู้ว่าพังเพราะอะไร): ระบบ K8s จะเก็บ Log ของ Container ตัวก่อนหน้า (ก่อนที่จะพังแล้วโดนสั่ง Restart) ไว้ให้ดูด้วย flag -p หรือ --previous bash kubectl logs -p kafka-cluster-kafka- 0 -n kafka-prod
Use code with caution. กรองดูเฉพาะคำสำคัญ (เช่น Start หรือ Error): bash kubectl logs kafka-cluster-kafka- 0 -n kafka-prod | grep -E "Starting|started|restarting"
Use code with caution.   ขั้นตอนที่ 3: ตรวจสอบระดับระบบ (หาก Log ใน Pod ไม่บอกอะไรเลย)   หากต้องการดูว่าทำไมอยู่ๆ Kafka ถึงโดนสั่ง Restart (อาจจะเกิดจากเครื่อง RAM เต็ม หรือโดนระบบสั่งฆ่า OOMKilled) ให้ใช้คำสั่งดู Events ของ Pod นั้นครับ:   bash kubectl describe pod kafka-cluster-kafka- 0 -n kafka-prod

## Q3
**You:** คุณใช้ Strimzi Operator หรือ Helm (Bitnami) ในการรัน Kafka? >> Strimzi ตอนนี้เจอ Error หรือมีอาการ CrashLoopBackOff (Restart วนไปเรื่อยๆ) หรือเปล่าครับ? >> ใช่แล้ว แต่หา log ไม่เจอ เพราะไม่รู้เป็นที่ cluster ไหน ตอนนี้มีคนแก้ไปแล้วโดยการ stop & start ใหม่

**AI:** เข้าใจเลยครับ อาการ CrashLoopBackOff ของ Kafka บน Strimzi Operator เป็นเรื่องที่เจอบ่อยมาก และการกด Stop & Start ใหม่ (หรือการลบ Pod ให้มันเกิดใหม่) มักจะช่วยแก้ปัญหาเฉพาะหน้าได้เพราะมันเป็นการล้าง State ชั่วคราวหรือย้ายไปรันบน Node ที่สมบูรณ์กว่า   แต่ถ้าในอนาคตเกิดเหตุการณ์นี้อีก แล้วคุณจำไม่ได้หรือไม่รู้ว่ามันพังที่ Cluster ไหน หรือ Pod ตัวไหน ให้ใช้สูตรลัดคอมมานด์ไลน์เหล่านี้ในการตามหาตัวปัญหาได้ทันทีครับ:   1. วิธีหาว่า Kafka Cluster ไหนกำลังพัง (คัดกรองด่วน) ถ้าในโปรเจกต์มีหลาย Cluster หรือหลาย Namespace ให้ใช้คำสั่งระดับ Global เพื่อหา Pod ที่ติดสถานะผิดปกติ:   หา Pod ที่ไม่ได้อยู่ในสถานะ Running (รวม CrashLoopBackOff ทั้งหมด): bash kubectl get pods --all-namespaces --field-selector status.phase!=Running
Use code with caution. ดูสถานะของ Strimzi Kafka Custom Resource โดยตรง: Strimzi มีคำสั่งเฉพาะในการเช็กสุขภาพของ Cluster ถ้าตัวไหนพัง สถานะ (Status) จะฟ้องทันที: bash kubectl get kafka --all-namespaces
Use code with caution. (ให้สังเกตช่อง READY หรือ STATUS หากเป็น False หรือ NotReady แสดงว่า Cluster นั้นกำลังมีปัญหา)   2. เทคนิคการคุ้ย Log ย้อนหลัง (หลังจากการ Stop/Start ไปแล้ว) เนื่องจากเพื่อนร่วมงานได้ทำการ Restart ไปแล้ว Log ใน Container ปกติจะถูกลบและเริ่มนับหนึ่งใหม่ แต่เรายังพอมีวิธีสืบสวนย้อนหลังได้ดังนี้ครับ:   เช็กเหตุการณ์ (Events) ย้อนหลังใน Namespace นั้น: Kubernetes จะเก็บประวัติประหลาดๆ เช่น Node เต็ม, เครื่องดับ, หรือ Pod โดนสั่งฆ่า ย้อนหลังไว้ประมาณ 1 ชั่วโมง: bash kubectl get events -n <ชื่อ-namespace> --sort-by= '.metadata.creationTimestamp'
Use code with caution.   ดู Log ของ Strimzi Operator (ตัวควบคุม): บางทีตัว Kafka Pod ไม่พัง แต่ตัว Operator สั่งงานไม่ได้ (เช่น Config ผิดพลาด หรือแก้ไฟล์ YAML แล้วพัง) ให้ไปดู Log ที่ตัวคุมระบบครับ: bash # หาชื่อ Pod ของ Strimzi Operator ก่อน
kubectl get pods -A | grep strimzi-cluster-operator
# ดู Log ของ Operator เพื่อดูว่ามันฟ้อง Error ตอนสั่งต้ม Kafka หรือไม่
kubectl logs <ชื่อ-strimzi-pod> -n <namespace-ของ-operator>
Use code with caution.   3. สาเหตุยอดฮิตของ Kafka + Strimzi ที่ทำให้เกิด CrashLoopBackOff รู้ไว้ก่อนเผื่อเจออีกรอบในวันข้างหน้า ส่วนใหญ่เกิดจาก 3 สาเหตุนี้ครับ:   Out of Memory (OOMKilled): Kafka ใช้ RAM เกินโควตาท่ีตั้งไว้ใน Resource Limits ระบบ K8s เลยสั่งฆ่าทิ้งทันที (เช็กได้จากคำสั่ง kubectl describe pod แล้วเจอคำว่า OOMKilled )   Storage เต็ม / PVC Lock: ดิสก์ที่เก็บข้อมูล Kafka (พวก Zookeeper หรือ KRaft metadata) เต็ม หรือติด Lock ทำให้มันเขียนข้อมูลต่อตอน Start ไม่ได้   Network / Readiness Probe ล้มเหลว: Kafka สตาร์ทช้าเกินไป (เช่น ข้อมูลเก่าเยอะต้องคอย Replay log นาน) จนตัว Kubernetes คิดว่ามันตาย เลยสั่ง Restart มันวนไปเรื่อยๆ ทั้งๆ ที่มันกำลังพยายามโหลดข้อมูลอยู่   เพื่อเตรียมรับมือในครั้งถัดไป คุณสามารถบอกผมเพิ่มเติมได้นะครับ:   คุณมีระบบ Centralized Logging (เช่น Azure Monitor, ELK Stack, หรือ Grafana Loki) ต่อไว้กับ AKS ไหมครับ? (ถ้ามี จะสามารถดู Log ย้อนหลังได้เป็นวันๆ เลยโดยไม่ต้องง้อ command line) อยากได้วิธี ปรับตั้งค่า (Tune) ตระกูล Probe timeout ของ Strimzi เพื่อป้องกันไม่ให้มัน Restart ตัวเองไวเกินไปไหมครับ?   Share public link This public link shares a thread, which may include personal information.
